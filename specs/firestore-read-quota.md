# 스펙: Firestore 읽기 한도 초과 해결 (하루 요약 문서)

> 작성일: 2026-10-21 · 작성: 클로드 코드 (사용자 "2단계까지 해봐 완료해"로 승인)
> 표기: [검증] 확인된 사실 · [추정] 추측

## 1. 목표
- Firestore 무료 읽기 한도(5만/일) 초과를 막는다. 2026-10-20, 10-21에 한도가 차서 크롤러의 "오늘 완료 브랜드" 조회가 실패했다. [검증]

## 2. 원인
- 쓰기는 하루 약 2,350건이라 한도(2만)에 여유가 있다. 초과된 건 읽기다. [검증]
- 부품 탭(그래픽카드·메인보드·CPU·Microsoft)은 화면을 열 때마다 30일 × 상품 수를 읽는다. 그래픽카드 한 번이면 약 17,000건, 메인보드는 30일이 쌓이면 약 27,000건이다. [검증: 코드 + 10/20 수집 건수]
- 크롤러가 날짜 문서를 고칠 때마다 날짜 목록 배열이 새로 만들어졌다. 그래서 탭을 열어 둔 상태면 30일치를 처음부터 다시 읽었다(전체 실행 1회에 14번). [검증: 코드]
- 가격 변동 팝업은 상품 1개를 보려고 30일 × 브랜드 전체를 읽었다. [검증: 코드]

## 3. 변경
| 대상 | 변경 |
|---|---|
| crawler.js | 부품 카테고리를 저장할 때 하루 요약 문서 `compuzone_summary/{브랜드}/days/{날짜}`를 추가로 저장한다. 같은 날 다시 수집하면 기존 요약과 합친다. 진행률 기록은 5건마다에서 10건마다로 바꾼다. |
| daily-summary.js | 요약 문서를 만든다. 900KB가 넘으면 저장하지 않는다(메인보드 906건 ≈ 290KB). |
| backfill-summary.js + workflow | 최근 30개 날짜의 요약을 기존 문서로 채운다. 1회에 최대 15,000 읽기만 쓰고, KST 17:30에 매일 실행해 이어서 채운다. |
| useMultiDateProducts / useSummaryProducts | 요약 문서를 먼저 읽고, 없으면 기존 방식으로 읽는다. |
| usePriceHistory | 날짜마다 그 상품 문서 1건만 읽는다. |
| useAvailableDates | 날짜 목록이 실제로 바뀔 때만 새 배열을 만든다. |

- 기존 `compuzone_prices` 데이터와 구조는 그대로 둔다. 문서만 추가한다.

## 4. 예상 효과 (화면 1회 기준 읽기)
- 그래픽카드 탭: 약 17,000 → 30 (+ 날짜 목록 ~200)
- 메인보드 탭: 최대 약 27,000 → 30
- Summary 탭: 약 3,900 → 8
- 가격 변동 팝업: 최대 약 5,500 → 30
